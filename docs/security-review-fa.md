# بازبینی امنیتی اولیه — ODIN Assistant

**تاریخ:** ۲۰۲۶-۱۰-۱۲  
**دامنه:** بررسی ایستا و هدفمندِ پل Android/WebView، سیاست پشتیبان‌گیری، و مدل لایسنس آفلاین.  
**محدودیت:** این سند جایگزین آزمون نفوذ، بررسی کامل تمام مسیرهای JavaScript، یا آزمون روی دستگاه واقعی نیست. هیچ سوءاستفاده‌ای در این بازبینی اجرا نشده است.

## یافته‌ها

### SEC-01 — مقصد درخواست HTTP از پل نیتیو محدود نشده است
**شدت:** متوسط؛ در صورت وجود مسیر تزریق JavaScript می‌تواند شدیدتر شود.  
**محل:** `android/app/src/main/java/com/odin/assistant/Bridge.java`، متد `http(...)`.

پل HTTP اکنون URL اولیه را بررسی می‌کند: فقط schemeهای HTTP/HTTPS، میزبان غیرخالی و URL بدون user-info پذیرفته می‌شود. روش درخواست به GET/POST/HEAD محدود شده، بدنهٔ درخواست حداکثر ۱ MiB و پاسخ بافرشده حداکثر ۴ MiB است. با این حال، ریدایرکت‌ها هنوز به‌صورت خودکار دنبال می‌شوند و مقصد هر ریدایرکت جداگانه اعتبارسنجی نمی‌شود؛ بنابراین این اصلاح کاهش ریسک است، نه رفع کامل SEC-01.

**اقدام بعدی:** فهرست میزبان‌های واقعی را از مصرف‌کننده‌های JS استخراج کنید و تست‌های خودکار برای URLهای نامعتبر، روش‌های ممنوع، سقف اندازه و رفتار ریدایرکت اضافه کنید. پیش از allowlist میزبان‌ها باید دامنه‌های واقعی داده‌ها مشخص شوند تا واکشی خبر و بازار ناخواسته نشکند.

### SEC-02 — رابط JavaScript نیتیو توانایی بازکردن URL دلخواه را دارد
**شدت:** پایین تا متوسط، وابسته به مسیر فراخوانی.  
**محل:** `Bridge.openExternal(String url)`.

متد ورودی را مستقیماً به `Uri.parse` و `Intent.ACTION_VIEW` می‌دهد و scheme یا مقصد را محدود نمی‌کند. اگر ورودیِ کنترل‌شده به این متد برسد، ممکن است برنامه‌های دیگری با URIهای غیرمنتظره باز شوند.

**اقدام انجام‌شده در شاخهٔ PR:** متد `Bridge.openExternal` اکنون فقط URLهای دارای میزبان معتبر و schemeهای HTTP/HTTPS را می‌پذیرد و URLهای دارای user-info را رد می‌کند. مسیریابی لینک‌های WebView نیز به همین قواعد محدود شده است. هنوز تست‌های خودکار اختصاصی برای این اعتبارسنجی اضافه نشده‌اند؛ این تغییر نیازمند CI و تست روی دستگاه است.

### SEC-03 — پشتیبان‌گیری Android فعال است
**شدت:** نیازمند تصمیم محصول/حریم خصوصی؛ نشت داده تأیید نشده است.  
**محل:** `android/app/src/main/AndroidManifest.xml`، ویژگی `android:allowBackup="true"`.

پل، تنظیمات، ژورنال و وضعیت لایسنس را در `SharedPreferences` با نام `odin` نگه می‌دارد. فعال بودن backup به‌تنهایی ثابت نمی‌کند همهٔ این داده‌ها روی همهٔ نسخه‌های Android پشتیبان‌گیری یا افشا می‌شوند؛ رفتار دقیق به نسخهٔ سیستم و قواعد انتقال داده وابسته است.

**اقدام پیشنهادی:** تصمیم روشن بگیرید که ژورنال و تنظیمات باید قابل‌بازیابی باشند یا نه. سپس قواعد `dataExtractionRules` و `fullBackupContent` را تعریف کنید تا داده‌های قابل‌انتقال و غیرقابل‌انتقال، به‌ویژه وضعیت وابسته به دستگاه، صریح باشند. کورکورانه backup را خاموش نکنید؛ این کار ممکن است بازیابی ژورنال کاربر را از بین ببرد.

### SEC-04 — راز HMAC لایسنس در بستهٔ توزیعی قرار دارد
**شدت:** محدودیت ساختاری مدل لایسنس آفلاین.  
**محل:** `src/license.py` و همتای JavaScript در `android/app/src/main/assets/www/js/license.js`.

کد مستند کرده است که secret در بسته قرار دارد و در برابر مهندسی معکوس حرفه‌ای مصون نیست. در مدل کاملاً آفلاین، secret مشترکی که داخل برنامهٔ توزیعی قرار دارد را نمی‌توان راز قابل‌اعتماد دانست؛ مهاجم مصمم ممکن است آن را استخراج کند. این باگ تازه‌ای نیست، اما باید به‌عنوان محدودیت امنیتی پذیرفته‌شده ثبت بماند.

**اقدام پیشنهادی:** اگر نیازمندی امنیتی سخت‌تر شد، امضاهای نامتقارن را بررسی کنید: کلید خصوصی فقط نزد صادرکننده بماند و اپ فقط کلید عمومی را برای اعتبارسنجی داشته باشد. مهاجرت باید سازگاری با کلیدهای صادرشده و مسیر ارتقای کاربران را مشخص کند.

## اصلاحات انجام‌شده در شاخهٔ PR

- `Bridge.openExternal`: رد schemeهای غیر وب، میزبان خالی و URLهای دارای user-info.
- `MainActivity.shouldOverrideUrlLoading`: بازکردن خارجی فقط برای URLهای معتبر HTTP/HTTPS؛ schemeهای دیگر داخل اپ یا بیرون از آن اجرا نمی‌شوند.
- `O.safeExternalUrl` در `js/ui.js`: اعتبارسنجی ساختاری URL در لایهٔ JS نیز انجام می‌شود؛ مسیر مرورگرِ توسعه دیگر schemeهای دلخواه را به `window.open` نمی‌دهد و از `noopener,noreferrer` استفاده می‌کند.
- `tests/js/test_external_url.js`: تست‌های منفی و مثبت برای HTTP/HTTPS، URL نسبی، `javascript:`, `file:`, `intent:`, `data:` و user-info اضافه شد.
- `Bridge.http`: اعتبارسنجی URL اولیه، محدودکردن روش‌ها به GET/POST/HEAD، سقف ۱ MiB برای بدنه و سقف ۴ MiB برای پاسخ بافرشده.

این تغییرات سطح حمله را کاهش می‌دهند، اما ریدایرکت‌های HTTP هنوز اعتبارسنجی مقصد به مقصد ندارند و تست‌های اختصاصی این قواعد نیز هنوز اضافه نشده‌اند. اصلاحات به‌تنهایی همهٔ ریسک‌های WebView یا تزریق JavaScript را رفع نمی‌کنند.

## مواردی که در این مرحله تغییر داده نشدند

- اعتبارسنجی مقصد هر ریدایرکت و allowlist میزبان‌ها هنوز پیاده‌سازی نشده است؛ ابتدا باید مقصدهای واقعی اپ مشخص شوند.
- `allowBackup` عمداً بدون تصمیم دربارهٔ بازیابی ژورنال تغییر نکرد.
- مدل لایسنس آفلاین تغییر نکرد؛ تغییر آن نیازمند طراحی سازگاری کلیدها و مسیر مهاجرت است.

## مرحلهٔ بعد برای ممیزی کامل‌تر

1. فهرست تمام فراخوانی‌های `ODINNative.http` و `ODINNative.openExternal` را در فایل‌های JS استخراج و مقصدهای مجاز را ثبت کنید.
2. مسیرهای ورود محتوای RSS/خبر و نحوهٔ درج آن در DOM را برای XSS بررسی کنید.
3. قواعد پشتیبان‌گیری را بر اساس تصمیم حفظ/عدم حفظ ژورنال بنویسید و روی نسخه‌های Android هدف تست کنید.
4. تست امنیتی و سازگاری را به CI اضافه کنید؛ سپس APK را روی دستگاه واقعی و چند نسخهٔ Android آزمایش کنید.
