## ۱. جمع‌بندی مدیریتی

پروژه یک برنامهٔ تحلیل و پیشنهاد سیگنال فارکس/طلاست؛ معاملهٔ خودکار یا اتصال به بروکر ندارد. هستهٔ تحلیل در دو پیاده‌سازی Python و JavaScript نگهداری می‌شود و تست‌های parity/golden برای کاهش اختلاف دو موتور وجود دارد. نسخهٔ Android رابط WebView محلی دارد و بخشی از کارهای نیتیو را با Java bridge انجام می‌دهد؛ سرویس پیش‌زمینه برای تکرار چرخهٔ تحلیل و اعلان‌ها نیز دارد. ریشهٔ مخزن همچنان کد دسکتاپ Windows/Python و ابزارهای بسته‌بندی آن را نگه می‌دارد؛ بنابراین «فقط اندروید» توصیف محصول جاری در README است، نه اینکه کد دسکتاپ از مخزن حذف شده باشد.

### وضعیت فعلی
- تست CI (Python self-test و smoke/parity tests جاوااسکریپت): **موفق** روی کامیت مبنا.
- ساخت APK با Gradle: **موفق** روی کامیت مبنا.
- بررسی امضای APK در این اجرا: **رد شده/اجرا نشده (skipped)** چون تنظیمات امضای release فراهم نبوده یا این اجرا در مسیر انتشار تگ نبوده است؛ بنابراین این CI، امضاشدن APK را ثابت نمی‌کند.
- تست واقعی روی دستگاه فیزیکی، آزمون چند نسخهٔ Android و اعتبارسنجی عملی چرخهٔ پس‌زمینه: **انجام نشده**.
- مقصد ریدایرکت‌های HTTP: **هنوز محدود یا اعتبارسنجی نشده**.
- PR تغییرات انتقال/امنیت: **باز**؛ تغییرات هنوز روی `main` نیستند.

## ۲. نقشهٔ معماری

### لایهٔ داده
- Android JS: `js/data.js` با تابع `O.http` و دریافت داده از Yahoo Finance، اسکنر TradingView، تقویم اقتصادی و فیدهای RSS.
- Python: `src/data/` و `src/fundamental/` برای منابع بازار، تقویم و اخبار.
- پل نیتیو: `Bridge.http` در `android/app/src/main/java/com/odin/assistant/Bridge.java` درخواست را در thread پس‌زمینه اجرا می‌کند و نتیجه را از طریق `ODIN.httpDone` به JS برمی‌گرداند.
- در مرورگر/Node، `O.http` به `fetch` برمی‌گردد؛ بنابراین قواعد اعتبارسنجی Native لزوماً در محیط مرورگر تکرار نمی‌شوند.

### تحلیل و تصمیم
- شاخص‌ها و تحلیل تکنیکال: `src/analysis/` و همتایان JS.
- اخبار و تقویم: `src/fundamental/` و `js/news.js` / `js/calendar.js`.
- استراتژی‌ها: `src/strategies/` و ماژول‌های JS متناظر.
- داور و vetoها: `src/judge/` و `js/judge.js`; تنظیمات Android در `js/config.js`.
- pipeline، registry و قرارداد پلاگین: `src/core/`، `src/plugins/` و `js/plugins.js`.
- ژورنال/پیگیری نتیجه: `src/journal/` و `js/journal.js`.
- UI اندروید: `index.html` + فایل‌های JS/CSS محلی؛ رندر در WebView.
- Android lifecycle: `MainActivity.java`, `OdinService.java`, `BootReceiver.java`, `Notif.java`.
- نسخه: `src/app_paths.py` مرجع نسخه است و Gradle آن را برای `versionName/versionCode` می‌خواند.

### مسیر یک چرخهٔ تحلیل به‌طور خلاصه
۱. خواندن تنظیمات و نمادها → ۲. دریافت OHLC/تأییدیه/تقویم/اخبار → ۳. محاسبهٔ شاخص‌ها و تحلیل‌ها → ۴. اجرای استراتژی‌ها → ۵. داوری، veto و امتیازدهی → ۶. ثبت ژورنال و ضداسپم → ۷. اعلان/رندر/ذخیرهٔ state → ۸. در حالت پس‌زمینه، زمان‌بندی چرخهٔ بعدی توسط سرویس.

## ۳. یافته‌های اولویت‌بندی‌شده

### P1 — مقصد ریدایرکت HTTP اعتبارسنجی نمی‌شود
**وضعیت:** باز.  
`Bridge.http` اکنون URL اولیه را به HTTP/HTTPS محدود می‌کند، میزبان خالی و user-info را رد می‌کند، روش‌ها را به GET/POST/HEAD محدود می‌کند، بدنه را به ۱ MiB و پاسخ بافرشده را به ۴ MiB محدود می‌کند. اما `setInstanceFollowRedirects(true)` فعال است؛ مقصدهای بعدی بدون بررسی مجدد دنبال می‌شوند. در نتیجه محدودکردن URL اولیه به‌تنهایی مانع هدایت درخواست به میزبان دیگری، از جمله میزبان محلی/خصوصی، نمی‌شود.

**اقدام بعدی:** فهرست مقصدهای واقعی را از `js/config.js` و مسیرهای داده استخراج کنید؛ سپس ریدایرکت را به‌صورت دستی با سقف تعداد، اعتبارسنجی هر مقصد و جلوگیری از downgrade از HTTPS به HTTP دنبال کنید. اگر میزبان‌های سفارشی کاربر مجازند، سیاست باید این نیاز را صریحاً لحاظ کند. برای هر تغییر، تست‌های رگرسیون و تست سازگاری فیدها لازم است.

### P1 — مسیر XSS در HTML تولیدی نیازمند تست امنیتی صریح است
**وضعیت:** ریسک قطعی exploit اثبات نشده؛ تست‌های اختصاصی ناقص‌اند.  
فیدهای RSS دادهٔ بیرونی‌اند. `js/news.js` از regex برای استخراج XML استفاده می‌کند و `stripHtml/cleanTitle` را به کار می‌برد؛ این‌ها sanitizer کامل HTML/XML نیستند. UI عمدتاً از escape در اجزای مشترک استفاده می‌کند، اما `app.js` چند sink از نوع `innerHTML` دارد و `O.modal(title, bodyHtml)` عمداً HTML می‌پذیرد. این الگو فقط وقتی ایمن است که دادهٔ بیرونی قبل از ورود به رشته‌های HTML escape شده باشد.

**اقدام بعدی:** تست‌های مخرب با عنوان/خلاصهٔ شامل `<img onerror=...>`, نقل‌قول، entityهای رمزگشایی‌شده و لینک‌های دارای scheme نامعتبر اضافه کنید. هر فیلد خبری باید هنگام رندر escape شود و URL لینک خبر باید به HTTP/HTTPS معتبر محدود بماند. تا زمانی که این تست‌ها اجرا نشده‌اند، XSS را «رد شده» تلقی نکنید.

### P1 — امضای APK برای انتشار تأیید نشده
**وضعیت:** نیازمند تنظیم release signing.  
اجرای build موفق شد، ولی مرحلهٔ `Verify signature` اجرا نشده بود. بیلد موفق فقط ثابت می‌کند APK ساخته و artifact بارگذاری شده است؛ نه اینکه APK برای انتشار نهایی با کلید معتبر امضا شده باشد.

**اقدام بعدی:** وضعیت keystore/secrets را بررسی کنید، از افشای کلید در مخزن جلوگیری کنید، یک build تگ‌شدهٔ کنترل‌شده بسازید و مرحلهٔ تأیید امضا و fingerprint گواهی را بررسی کنید. انتشار نهایی بدون اثبات امضا و کنترل artifact انجام نشود.

### P2 — پشتیبان‌گیری Android روشن است
**وضعیت:** تصمیم محصول/حریم خصوصی لازم است، نشت داده اثبات نشده.  
`AndroidManifest.xml` دارای `android:allowBackup="true"` است. داده‌هایی مانند تنظیمات، ژورنال و وضعیت لایسنس در `SharedPreferences("odin")` نگهداری می‌شوند. خاموش‌کردن کورکورانهٔ backup ممکن است بازیابی ژورنال را از بین ببرد.

**اقدام بعدی:** تصمیم بگیرید چه داده‌ای باید از backup و انتقال دستگاه مستثنا باشد؛ سپس `dataExtractionRules` و `fullBackupContent` را صریح تعریف و رفتار را روی نسخه‌های هدف آزمایش کنید.

### P2 — مدل لایسنس آفلاین در برابر مهندسی معکوس مقاوم کامل نیست
**وضعیت:** محدودیت معماری شناخته‌شده، نه باگ تازهٔ اثبات‌شده.  
راز HMAC در کد توزیعی قرار دارد؛ در نتیجه مهاجم مصمم می‌تواند آن را استخراج کند. تست‌های موجود سازگاری SHA/HMAC، بردهای ثابت، تاریخ انقضا، device ID و عقب‌کشیدن ساعت را بررسی می‌کنند؛ اما این تست‌ها secret را در برابر استخراج محافظت نمی‌کنند.

**اقدام بعدی:** اگر تهدید مورد انتظار از دورزدن محلی بیشتر شد، امضای نامتقارن را طراحی کنید؛ کلید خصوصی نزد صادرکننده و کلید عمومی در اپ باشد. این کار باید مسیر مهاجرت و سازگاری با لایسنس‌های صادرشده را تعریف کند.

### P2 — مدیریت lifecycle/درخواست‌های هم‌زمان نیازمند آزمون روی دستگاه است
**وضعیت:** نیازمند آزمون اجرایی.  
پل HTTP از pool ثابت چهار thread استفاده می‌کند و JS pending callbacks را نگه می‌دارد. چرخهٔ سرویس از WebView بی‌سر استفاده می‌کند. timeout شبکه وجود دارد، اما تعداد درخواست‌های صف‌شده و رفتار توقف/شروع سرویس و WebView در شرایط واقعی با تست‌های unit فعلی کامل پوشش داده نشده‌اند.

**اقدام بعدی:** تست قطع اینترنت، پاسخ کند، چرخهٔ هم‌زمان، توقف سرویس، ری‌استارت گوشی، محدودیت باتری و callback پس از نابودی WebView را به ماتریس تست دستی/خودکار اضافه کنید.

### P3 — داده‌های کلان و خروجی heuristic ممکن است کهنه یا تقریبی باشند
**وضعیت:** محدودیت محصول/داده، باید شفاف بماند.  
اخبار بر پایهٔ واژگان و قواعد heuristic تحلیل می‌شوند، نه مدل درک کامل متن. نرخ‌های carry در تنظیمات با برچسب تاریخ `2026-09` ثابت هستند. Yahoo، TradingView و فیدهای RSS منابع ثالث‌اند و قالب، دسترسی یا تأخیر آن‌ها ممکن است تغییر کند.

**اقدام بعدی:** زمان آخرین به‌روزرسانی و کهنگی هر منبع را در UI نشان دهید؛ دادهٔ ناموجود را با دادهٔ معتبر اشتباه نگیرید؛ نرخ‌های ثابت را با تاریخ و فرایند بازبینی روشن نگه دارید؛ صحت استراتژی را با backtest و دادهٔ خارج از نمونه ارزیابی کنید، نه فقط با تست‌های واحد.

## ۵. قرارداد توسعه برای فازهای بعدی

۱. `main` مرجع اصلی مخزن است؛ نام‌های `ANDROID` و `android` فعلاً تاریخی‌اند.  
۲. هر فاز باید کوچک، مستقل، قابل بازگشت و همراه با معیار پذیرش مشخص باشد.  
۳. برای منطق مشترک، تغییر Python و JavaScript باید همراه تست parity/golden باشد.  
۴. تغییرات UI باید smoke tests و بررسی رندر را حفظ کند؛ تست خودکار جای تست دستگاه نیست.  
۵. تغییر در schema ذخیره‌سازی، لایسنس، pipeline یا ترتیب مراحل باید مستند و دارای تست مهاجرت/رگرسیون باشد.  
۶. هیچ دادهٔ ناموجودی نباید به سیگنال معتبر تبدیل شود؛ اصل fail-closed و توضیح دلیل رد سیگنال حفظ شود.  
۷. تغییرات امنیتی باید با تست منفی و تست سازگاری منابع واقعی همراه باشند.  
۸. انتشار فقط پس از build تگ‌شده، تأیید امضا، بررسی artifact و smoke test روی دستگاه انجام شود.

## ۶. ترتیب پیشنهادی ادامهٔ کار

**فاز A — بستن ریسک‌های پایه**
1. تست‌های امنیتی و رگرسیون برای اعتبارسنجی URL/redirect و سقف اندازه.
2. تست‌های XSS برای داده‌های RSS و تمام مسیرهای ورود به `innerHTML`.
3. تعیین سیاست backup و تأیید مسیر امضای APK.
4. به‌روزرسانی PR و اجرای CI نهایی.

**فاز B — تثبیت runtime اندروید**
1. آزمون چرخهٔ foreground service، boot، Doze، اعلان‌ها و قطع/وصل شبکه روی دستگاه.
2. ثبت ماتریس نسخه‌های Android/دستگاه و خطاهای بازتولیدپذیر.
3. بررسی عملکرد مصرف باتری، صف درخواست‌ها و رندر UI.

**فاز C — توسعهٔ محصول**
1. انتخاب یک قابلیت یا مشکل واحد با معیار پذیرش قابل اندازه‌گیری.
2. تعریف رفتار مورد انتظار، تست‌های golden و تأثیر بر نسخهٔ Python/Android.
3. پیاده‌سازی در یک PR کوچک، اجرای CI، بررسی diff و سپس انتشار آزمایشی.

## ۷. نتیجه

پروژه برای **ادامهٔ توسعهٔ مرحله‌ای** پایهٔ مناسبی دارد: ساختار ماژولار، تست‌های Python/JS و مرجع واحد نسخه از نقاط قوت‌اند. اما برای اعلام آمادگی انتشار نهایی، امضای APK، آزمون دستگاه واقعی، اعتبارسنجی مقصد ریدایرکت‌ها و تست‌های امنیتی XSS باید تکمیل شوند. این موارد باید به‌عنوان بدهی فنی باز در برنامهٔ توسعه بمانند، نه اینکه موفقیت CI به‌عنوان رفع آن‌ها تفسیر شود.
