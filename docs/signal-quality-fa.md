# 🎯 کیفیت سیگنال — نسخهٔ ۱٫۶٫۰

> این سند به زبان ساده می‌گوید: از کجا شروع کردیم، چه چیزی ساخته شد، و
> قدم بعدی چیست. سه تغییرِ این نسخه همه **قابل خاموش‌کردن** و **قابل اندازه‌گیری**
> هستند و هیچ‌کدام رفتار پیش‌فرض برنامه را عوض نمی‌کنند.

---

## ۱. نقطهٔ شروع (واقعیت عددی)

بک‌تست نسخهٔ ۱٫۲٫۰ روی ۲۴ ماه داده:

| شاخص | مقدار |
|---|---|
| معامله | ۱٬۴۸۵ |
| نرخ برد | ۳۲٫۹٪ |
| میانگین هر معامله | **−۰٫۰۳۲R** |
| ضریب سود (PF) | ۰٫۹۴۶ |
| حداکثر افت | −۴۹R |

با نسبت سود به زیان ۱:۲، نقطهٔ سربه‌سر **۳۳٫۳٪** است. یعنی سیستم دقیقاً روی
خط ایستاده و فقط هزینهٔ اسپرد آن را منفی کرده. این یعنی:

> **مسئله «کمبود اندیکاتور» نیست؛ مسئله «ترکیبِ نامناسب سیگنال‌ها» است.**

سه ستاپ (پولبک در روند / بازگشت از رنج / شکست تازه) با **یک آستانهٔ مشترک**
داوری می‌شدند و هیچ گزارشی نمی‌گفت کدام‌شان پول می‌سازد و کدام‌شان می‌سوزاند.

---

## ۲. چه چیزی اضافه شد (به ترتیب اولویت)

### ۱) چراغ‌قوه: سه برش تشخیصی در بک‌تست
`tools/backtest.py` حالا در گزارش، سه جدول تازه می‌دهد:

| جدول | سؤالش |
|---|---|
| **به تفکیک امتیاز** (`per_score`) | سیگنال‌های امتیاز ۵، ۶، ۷، ۸… چقدر سود می‌دهند؟ |
| **به تفکیک ساعت ورود** (`per_hour`) | کدام ساعت‌های روز انتظار منفی دارند؟ |
| **به تفکیک روز هفته** (`per_weekday`) | دوشنبه/جمعه فرق دارند؟ |

بدون این سه، هر تنظیمی حدس است. با این‌ها می‌شود تصمیم گرفت.

### ۲) دروازهٔ استراتژی (`strategy_gate`)
هر ستاپ می‌تواند **خاموش** شود یا **آستانهٔ امتیاز خودش** را داشته باشد:

```yaml
judge:
  strategy_gate:
    enabled: true                    # پیش‌فرض: false (رفتار قبلی)
    trend_pullback:  {enabled: true,  min_score: 5}
    breakout:        {enabled: true,  min_score: 7}
    range_reversion: {enabled: false}   # کاملاً خاموش
```

- ستاپ خاموش → سیگنال صادر نمی‌شود و دلیلش صریح در «قیف» ثبت می‌شود
  (`STRATEGY_OFF`) — نه سکوت مرموز.
- `min_score` اختصاصی → همان ستاپ باید امتیاز بالاتری بیاورد.
- **در هر دو موتور پیاده شد:** پایتون (`src/judge/scoring.py`) و JS اندروید
  (`www/js/judge.js` + پیش‌فرض در `config.js`)؛ هر دو با تست قفل شده‌اند.
- پیش‌فرض `enabled: false` است، پس اگر کاری نکنی هیچ‌چیز عوض نمی‌شود.

### ۳) جاروی آستانهٔ امتیاز (`--sweep-min-score`)
یک فرمان، چند آستانه، همان داده:

```bash
python tools/backtest.py --data-dir ~/odin-m15 --sweep-min-score 5,6,7,8
```

خروجی: جدول مقایسه (تعداد معامله، نرخ برد، میانگین R، PF، افت) + یک فایل
`sweep-min-score.md` و یک **پیشنهاد صریح**:

> معیار پیشنهاد = بیشترین میانگین R میان آستانه‌هایی که **حداقل ۱۰۰ معامله**
> دارند. آستانهٔ خوش‌شانس با ۱۲ معامله برندهٔ گزارش نمی‌شود.
> و در پایان گزارش نوشته می‌شود که این پیشنهاد باید در یک بازهٔ دوم
> (واک‌فوروارد) هم دیده شود.

## ۳. چطور استفاده کنم؟ (سه گام)

```bash
# گام ۱ — ببین کدام ستاپ و کدام امتیاز سود می‌دهد
python tools/backtest.py --data-dir ~/odin-m15 --label "پایه"
#   → در گزارش: «به تفکیک استراتژی» و «به تفکیک امتیاز»

# گام ۲ — آستانهٔ درست را پیدا کن (بدون تغییر config)
python tools/backtest.py --data-dir ~/odin-m15 --sweep-min-score 5,6,7,8
#   → sweep-min-score.md

# گام ۳ — تصمیم را در config بنشان (و در بازهٔ دوم هم بسنج)
#   ستاپِ با میانگین R منفی → enabled: false
#   ستاپِ سودده ولی کم‌نمونه → min_score بالاتر
python tools/backtest.py --data-dir ~/odin-m15 --from 2024-01-01 --to 2024-12-31
python tools/backtest.py --data-dir ~/odin-m15 --from 2025-01-01 --to 2025-12-31
```

**قاعدهٔ طلایی:** تصمیمی که فقط در یک بازه سود می‌دهد، تصمیم نیست؛ فیت‌شدن
روی گذشته است.

## ۴. چه چیزی عمداً انجام نشد (و چرا)

| ایده | چرا نه (فعلاً) |
|---|---|
| مدیریت خروج (BE/پلکانی/تریلینگ) | موتور بک‌تست فعلاً فقط TP/SL خالص دارد؛ افزودنش تغییر ساختاری است و باید نسخهٔ جداگانه با تست داشته باشد |
| گیت همبستگی سبد | به دادهٔ همبستگی لحظه‌ای نیاز دارد؛ اثرش روی **افت** است نه نرخ برد |
| بایاس تایم‌فریم روزانه | نیازمند داده و محاسبهٔ D1 در هر دو موتور (پایتون + JS) |
| تغییر آستانهٔ ۵ به عددِ دستی دیگر | همان کاری است که جارو مکانیکی و بی‌سوگیری انجام می‌دهد |

## ۵. آنچه باید انتظار داشته باشیم

اگر گزارش نشان دهد یکی از سه ستاپ میانگین R منفی دارد:

- **حذف یا سخت‌کردن** آن ستاپ معمولاً **+۰٫۰۵ تا +۰٫۱R** روی کل می‌دهد —
  یعنی عبور از خط سربه‌سر.
- هزینه‌اش: تعداد سیگنال کمتر. برای جبرانش، مسیر بعدی «مدیریت خروج» و
  «سایزینگ بر پایهٔ رده» است، نه شل‌کردن آستانه.

تست‌ها: `tests/test_signal_quality.py` (پایتون) و بخش تازهٔ
`tests/js/test_strategies.js` (اندروید) — هر دو بخشی از CI هستند.
